# LLM Gateway 架构设计

本文说明网关在路由、故障处理、限流配额、用量结算和扩容方面的设计取舍。重点是请求从进入网关到完成结算时，哪些状态必须保持一致，哪些能力可以降级，以及系统在流量扩大后应先改哪里。

## 设计目标

网关面对的不是普通的 HTTP 转发，而是一个带有余额、Token、渠道健康状态和审计账单的请求执行系统。因此设计优先级是：

1. 不因为单个上游渠道故障拖垮整体服务。
2. 不重复扣费，不把同一请求记成多次成功。
3. 限流和配额在多实例下仍有统一语义。
4. 流式响应已经交付给用户后，不尝试做语义不可靠的“续接”。
5. 在保证账务正确的前提下，健康记录和统计指标允许 best-effort。

当前实现使用 Go `net/http`、PostgreSQL 和独立 nginx 托管的 React Dashboard。nginx 将管理端和下游 API 反向代理到 Go 网关；各业务模块在自身包内定义窄 port，进程边界负责组合这些 port；代理编排集中在 `server/internal/proxy`，协议适配集中在 `server/internal/proxy/openai`。

## 1. 负载均衡与路由策略

### 1.1 先按 priority 做硬隔离

对一个 public model，系统先得到所有启用且有模型映射的渠道，再排除：

- 熔断状态为 `open` 的渠道。
- 半开状态但没有取得探测 lease 的渠道。
- 手动停用的渠道。
- 余额为零或负数的计费渠道。
- 余额低于全局 `CHANNEL_MIN_ROUTE_BALANCE` 的计费渠道。

剩余候选按 `priority` 分组，只在最高 priority 组内选择首选渠道。低 priority 渠道不是正常流量的竞争者，而是故障切换时的后备。

这样设计的原因是：priority 通常表达运营者的硬意图，例如主供应商、区域优先级、合同优先级或成本层级。如果把所有渠道放入一个动态分数池，低优先级渠道可能因为短期延迟更低而夺走主渠道流量，运营配置就失去可解释性。

### 1.2 同级使用 weight，保留运营控制

同一 priority 组内使用静态 weight 分配流量。weight 是基础流量比例，而不是绝对保证。比如两个渠道权重为 1 和 3，长期目标是约 25% 和 75%。

当前不实现按延迟和健康度动态改权重，原因是：

- 动态评分容易把请求长度、模型输出速度和网络延迟混在一起。
- 少量样本会造成权重剧烈抖动。
- 运营者难以解释某个渠道为什么突然得到大量或少量流量。
- 熔断已经承担“异常渠道隔离”的职责，不需要再用复杂评分重复表达。

### 1.3 使用 API Key + public model 粘性首选

同一个 API Key 使用同一个 public model 时，系统用 `APIKeyID + model` 做稳定哈希，再映射到最高 priority 候选组的权重区间。因此在候选集合没有变化时，连续请求会尽量落到同一渠道。

粘性解决的是连接复用、上游会话习惯、缓存命中和行为稳定性问题，但不是硬绑定：

- 渠道熔断后立即失效。
- 渠道余额不满足阈值后立即失效。
- 渠道被停用后立即失效。
- 单次请求失败时允许故障切换。

不把粘性写入数据库，是因为它是可重新计算的路由偏好，不是账务状态。只要哈希输入和候选顺序稳定，服务重启不需要恢复粘性表；同时避免每次请求多一次粘性读写。

代价是候选集合发生变化时可能重新分配，例如渠道被熔断、权重修改或新增渠道。这是有意接受的：健康性和运营配置优先于粘性。

### 1.4 为什么不使用最短队列或最低延迟

当前不使用“谁快选谁”或“谁当前请求少选谁”，因为这些策略需要高质量的实时指标，并且容易形成反馈回路：某渠道因为短期变快获得更多请求，负载上升后变慢，又被快速降权，最终造成流量震荡。

后续如果需要动态路由，应先建立独立的渠道运行指标，再采用平滑窗口、最小样本数、冷启动和探索流量，而不是直接把 usage log 的平均耗时放进路由热路径。

## 2. 上游故障处理

### 2.1 请求级故障切换

一次请求先生成去重后的候选顺序，最多尝试配置的 `UPSTREAM_MAX_ATTEMPTS` 次。可切换故障包括：

- 连接建立失败、DNS 失败、连接重置等传输错误。
- 上游超时。
- HTTP 429。
- HTTP 401、402、403。
- HTTP 5xx。

调用方错误如 400、404、409、422 不切换，因为这类错误通常是请求本身的问题。切换渠道无法修复一个错误的模型参数或消息格式，反而会放大上游请求量。

每次实际尝试都会更新对应渠道的健康状态，但客户端请求只允许有一个最终响应和一次最终结算。失败尝试不是成功 usage log，不应被当成多次用户请求扣费。

### 2.2 总时限和取消传播

请求使用一个总 `context` deadline，所有上游 HTTP 请求都从该 context 派生。客户端断开、服务关闭或总时限到期时：

- 当前上游请求被取消。
- 不再尝试后续渠道。
- 尚未结算的 quota 和 rate-limit reservation 释放或由 reaper 回收。

总时限比无限重试更重要。没有总时限时，多渠道故障切换可能把一个下游请求拖成多个上游慢请求，最终耗尽连接、goroutine 和数据库连接池。

### 2.3 流式请求中途挂断

流式请求分成两个阶段：

1. 上游返回 2xx，但网关尚未向下游成功写出任何数据。
2. 网关已经成功向下游写出 SSE 数据。

第一阶段仍可视为尚未提交，可以在协议解析失败或上游连接中断时选择其他候选。当前实现获得流式 2xx 后就把流交给 `completionStream`，因此不做复杂的首帧前缓冲切换。

第二阶段不能切换渠道。原因是已经发送的内容无法撤回，重新请求会导致：

- 用户收到重复内容或上下文不连续的内容。
- 两个上游生成任务无法可靠合并。
- 无法证明第二个渠道从哪个 token 继续。
- 计费和 usage 可能重复。

因此中途断流会结束当前 SSE，并记录渠道故障；客户端取消不计为渠道故障。

### 2.4 中途断流的计费

正常结束必须同时收到上游 usage 和 `[DONE]`，按上游实际 usage 原子结算。

如果中途断流、协议错误或客户端取消，网关只对已经成功写入下游的文本 delta 进行本地 tokenizer 估算：

- prompt 使用请求预检时的输入 Token 估算。
- completion 只累计成功执行 `emit` 的文本内容。
- 本地 tokenizer 失败或没有成功转发文本时不扣费。
- usage log 以 `partial_estimated_*` 错误码标记估算口径。

这是“可执行的已交付边界”，不是上游账单的绝对真值。不同供应商 tokenizer、工具调用、reasoning token、多模态内容可能存在差异，所以正常完成优先使用上游 usage，部分结算必须在审计中明确是估算值。

## 3. 限流与配额

### 3.1 为什么选择 PostgreSQL reservation

限流和业务配额都需要处理“请求已经进入，但还没有完成”的状态。只查询 `usage_logs` 会产生典型竞态：两个请求同时看到剩余额度，然后同时放行。

当前方案把请求生命周期拆成：

```text
申请 reservation -> 执行请求 -> 成功结算或失败释放 -> 过期回收
```

周期配额使用 PostgreSQL bucket 和 reservation；运行时限流使用独立的 rate-limit reservation。它们不共用持久化模型，因为周期预算和速率控制的业务语义不同。

金额使用定点整数/NUMERIC，Token 使用整数，数据库事务负责行锁和原子更新。

### 3.2 限流语义

当前支持 RPM、TPM、RPD 和 concurrency，作用域包括 global、user、api_key、model、channel。`tpd` 已废弃，日 token/费用预算由配额模块承担。

- 用户、Key、模型等请求前即可确定的规则先检查。
- 渠道规则在路由选出具体渠道后检查。
- Token 使用输入 Token 加最大输出 Token 的保守估算预留。
- 完成后按实际 usage 结算，多余预留释放。
- 失败、取消和正常结束都必须结束 reservation 生命周期。
- 超限动作仅保留 `reject`，立即返回 OpenAI 风格 `rate_limit_error`。

没有实现同步 queue，是因为排队会长期占用 HTTP 连接和 handler goroutine；对于长时间 LLM 请求，快速返回 429 并由调用方退避比网关内部无限等待更可控。

### 3.3 多实例是否会失效

只要所有实例连接同一个 PostgreSQL 集群，限流和配额不会因为横向扩展而各自计数。计数和 reservation 位于共享数据库，事务行锁负责竞争，实例本地不保存限流真相。

多实例仍有几个前提：

- 所有实例使用相同 schema 和迁移版本。
- 所有实例使用相同的限流规则和时钟语义，时间统一按 UTC。
- reservation 的过期时间和后台 reaper 正常运行。
- PostgreSQL 连接池足以承受申请、释放和结算请求。

如果每个实例单独使用 PostgreSQL，限流会失效，因为每个实例只看到自己的计数。这种部署不能称为共享限流集群。

在极高吞吐场景下，PostgreSQL 可能成为限流热行和事务瓶颈。届时可以把短窗口速率计数迁移到 Redis/Lua 或专用限流服务，但余额、配额、结算仍应以 PostgreSQL 为最终账务来源，不能让 Redis 成为费用真相。

## 4. 用量统计如何保证不丢、不重

### 4.1 成功请求

成功请求的核心动作在 Store 的一次事务中完成：

```text
锁定用户余额
锁定渠道余额（如适用）
结算 quota reservation
扣减用户/渠道余额
写入 success usage_log
提交事务
```

任何一步失败都回滚，避免出现“扣了余额但没有日志”或“写了成功日志但没有扣费”。

### 4.2 防止重复成功日志

`usage_logs.request_id` 有唯一约束，且结算会检查 reservation 状态和 request identity。重复调用同一个结算请求不会再次成功写账。

请求内 failover 使用同一个 request ID，最终只有成功候选进入结算。失败候选只更新渠道健康，不写成功 usage log。

### 4.3 失败请求和部分结算

失败请求仍可以写 error usage log，用于审计和渠道诊断。部分流式结算通过同一原子结算入口写入 usage log；如果结算失败，不会伪装成已扣费，而是释放/保留 reservation 交由生命周期处理，并记录结算失败诊断。

### 4.4 不丢的边界

数据库事务提交成功后，usage log 与余额状态同时持久化，即使网关随后崩溃也不会丢失已提交账单。

数据库事务提交前进程崩溃时，事务回滚；quota 和限流 reservation 的 pending 状态由主动释放和后台 reaper 兜底。这里的目标不是让每个中间事件都永久保存，而是保证最终账务状态不出现半提交。

### 4.5 统计接口的取舍

管理端统计从 usage_logs 实时聚合，而不是维护另一份可能漂移的统计表。优点是统计可重算、可审计；缺点是日志量大后聚合查询会成为读压力。

如果需要承受更大查询量，应增加异步 rollup 或物化视图，但 rollup 只能作为查询加速层，不能替代 usage_logs 和结算事务。

## 5. 瓶颈与百倍流量扩展路径

### 5.1 当前最可能的瓶颈

按影响顺序，当前瓶颈大致是：

1. PostgreSQL 事务和连接池：一次成功请求会涉及 reservation、余额锁、配额 bucket、usage log 和渠道余额。
2. usage_logs 的实时聚合：Dashboard 启动会并发请求多个统计接口，长时间日志表上会产生聚合压力。
3. 限流/配额热行：同一 global、user 或 API Key 的高并发请求会竞争同一 bucket 行。
4. 上游连接与流式响应：长连接会占用 HTTP transport、文件描述符和 goroutine。
5. 单体进程的管理端和代理流量共享资源：统计查询、管理操作和下游代理共用同一个服务进程。

CPU 和 Go 调度通常不会是第一瓶颈；LLM 请求的主要成本在网络等待、长连接和数据库事务。

### 5.2 扛住 100 倍流量的改造顺序

第一步不是马上引入 Redis，而是先建立基线：

- 记录请求 QPS、SSE 并发数、上游响应时间、数据库事务耗时。
- 记录 PostgreSQL 连接池使用率、锁等待、慢查询和各类 reservation 失败率。
- 为 usage 聚合查询执行 `EXPLAIN (ANALYZE, BUFFERS)`。
- 对比非流式、短流式和长流式请求的资源占用。

然后按以下顺序改造：

**第一阶段：代理进程和数据库的基础扩容**

- 网关多实例部署，前面加负载均衡器。
- PostgreSQL 使用独立实例、合理连接池、读副本或只读统计连接。
- 调整 HTTP transport 的连接复用、最大空闲连接和响应头超时。
- 保证所有实例共享同一 PostgreSQL，不在进程内保存限流真相。

**第二阶段：把统计读路径移出结算热路径**

- usage_logs 继续作为账务事实表。
- 增加按小时/天的异步 rollup 表或物化视图。
- Dashboard 和报表优先查询 rollup，明细和审计仍查询 usage_logs。
- rollup 任务使用幂等游标或时间分片，失败后可以重算。

**第三阶段：拆分高竞争限流计数**

- 将 RPM/TPM 等短窗口计数迁移到 Redis/Lua 或独立限流服务。
- 保留 PostgreSQL 作为配额、余额、reservation 最终来源。
- 明确 Redis 故障策略：通常是保护性拒绝，而不是无条件放行。

**第四阶段：拆分长连接和管理端流量**

- 代理服务独立扩容，管理端和统计查询独立部署。
- 通过连接数、内存和请求超时限制流式并发。
- 必要时引入异步任务 API，避免所有长任务都占用同步 HTTP 连接。

### 5.3 哪些事情不要先做

- 不要先用本地内存计数器解决多实例限流。
- 不要先用消息队列替代同步结算；这会引入账务最终一致性和重复扣费问题。
- 不要把每次请求的所有尝试都写成成功 usage log。
- 不要为了动态路由先引入机器学习或复杂 bandit 算法。
- 不要在没有指标基线前盲目扩大 PostgreSQL 连接池；连接数过大可能让数据库更早耗尽。

## 结论

当前架构的核心选择是：路由偏好可以近似、健康指标可以 best-effort，但余额、配额、限流 reservation 和成功用量结算必须由共享 PostgreSQL 以事务保证一致性。

这使系统适合先通过多实例和数据库优化扩展。真正达到 100 倍流量时，优先把统计查询和短窗口限流从 PostgreSQL 热路径中卸载，同时保留 PostgreSQL 作为余额和账务事实来源。这样扩容不会牺牲最难恢复的正确性。
